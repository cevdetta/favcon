# Decisions

Every row is backed by a measurement. The originals were taken over a 39-mark corpus that
does not ship with this repository; the ones marked **re-measured** have been reproduced
against `test/fixtures/`, and where the two disagree the reproducible number wins.
`docs/BENCHMARKS.md` is generated by `node bench/bench.mjs --write` and is the current truth.

## The accuracy bar

`pct <= 1.0 %` — the share of pixels whose colour distance from the reference exceeds 8/255,
measured on **both** a white and a black composite so that alpha error cannot hide in either.
Distance is the largest single-channel difference: an error has to be invisible in every
channel to pass, not merely small on average.

Reference = an unquantised resvg render of the **var-resolved source** at the same size — not
of favcon's own `icon.svg`, which would make the gate blind to the geometry error
`floatPrecision` introduces before a rasteriser is ever involved.

RMSE is reported alongside but does not gate: error is driven by *size*, not by the mark, so
one RMSE threshold is the wrong shape — at 16 px nearly every pixel is an anti-aliasing edge.

**The bar is a statement about the sizes favcon ships by default** — 180, 256 and 512. It is
not reachable at every size anyone might ask for, and pretending otherwise would make it
meaningless: a 32 px icon is 1024 pixels of which almost all are edges, and no palette
reproduces an anti-aliasing ramp to 8/255. The size curve is in `docs/BENCHMARKS.md`; the
same mark that scores 0.41 % at 256 px scores 11 % at 32 px with the same pipeline. If you
ask for `--sizes 16`, you get the best 16 px icon this pipeline can make, and it is not
within 8/255 of a reference render. Nothing is.

Three readings of "colour distance" were compared (largest channel, Euclidean/√3, mean
channel) and they agree to within 0.06 pp at the default sizes. The metric's shape does not
matter here: pixels that differ, differ by a lot, because palette snapping is a jump rather
than a drift.

## Priority

**Smaller output beats faster build.** The bytes ship to every visitor forever; the build
happens once. A change that costs bytes to save build time is rejected by default.

The accuracy bar is a *constraint*, not one side of that trade. Where bytes and the bar
conflict, the bar wins — which is what decision 6 below turns on.

### Decision 13, re-measured — it holds, but the stated reason was wrong

A cross-tool comparison looked like it refuted decision 13: `favicon.sh` renders four sizes at
once and finishes a like-for-like build in 12.5 s against favcon's 17.8 s, with user times
within 7 % of each other. That reading was wrong, and it was wrong in an instructive way —
the comparison confounds two variables, because `favicon.sh` also passes a bare `--zopfli`,
which is `--zi 15`, where favcon passes `--zi 120`.

Crossing the two axes under control — four jobs, identical work in every arm, three
interleaved repetitions, 16 cores:

| at once | `--zi` | wall | child CPU | cores | bytes |
|---|---|---|---|---|---|
| **1 (serial)** | **120** | **22.61 s** | 185.2 s | **8.2×** | 5539 |
| 4 | 120 | 22.28 s | 258.5 s | 11.6× | 5539 |
| 1 (serial) | 15 | 5.89 s | 46.3 s | 7.9× | 5585 |
| 4 | 15 | 5.66 s | 62.1 s | 11.0× | 5585 |

**Concurrency buys 1.4 %**, inside the run-to-run spread (20.94–25.30 s against
19.63–24.57 s). Decision 13's conclusion stands, and the whole 1.4× gap to `favicon.sh` is
the iteration count, not the scheduling.

But the *reason* decision 13 gave for it — "oxipng already saturates the machine on a single
file" — is false. One file reaches **8.2 of 16 cores**, nowhere near saturation. Four at once
reaches **11.6**, genuinely more throughput, and converts essentially none of it into
progress: **40 % more CPU burned for 1.4 % less wall clock**. The extra cores go into
contention, not work. That is a stronger argument for staying serial than the original, since
it says concurrency here is not merely useless but actively wasteful of a shared machine.

The `--zi` row is the one worth arguing about. Dropping 120 → 15 is **73.9 % faster for 46 B**
across four files — 0.8 %. Decision 8 takes that trade on the stated priority that bytes ship
forever and build time does not; it is recorded here in those terms so the trade can be
re-judged rather than assumed.

## Decisions taken during the build-out

These are new, and each one exists because something measured did not match what was
expected.

### 16. Tool resolution probes, it does not just look

A path on disk is not proof of a working tool. `pngquant-bin` installs
`node_modules/.bin/pngquant` as a Node script that execs a binary its postinstall downloads
separately — and that postinstall is skipped by `--ignore-scripts` and by npm's default
blocked-install-scripts policy. The shim is then present, executable, and fails at spawn time
with a Node stack trace where a PNG should be. It was the first thing the new resolver hit.

So every candidate is probed with `--version`, and a candidate that does not run falls
through to the next tier — which is what lets a machine with a broken shim still build using
the `pngquant` on `PATH`. `npm run` puts `node_modules/.bin` at the *front* of `PATH`, so
that shadowing is the common case, not an exotic one.

The version strings are not a by-product: the Astro cache is keyed on them, because all three
tools change their output bytes across releases and a cache keyed only on the SVG hands back
stale files after a `brew upgrade`, invisibly.

An explicit `FAVCON_RESVG` / `FAVCON_PNGQUANT` / `FAVCON_OXIPNG` override is the one
exception — it is a hard error rather than a fall-through, because quietly running a
different binary than the one that was named is worse than not running at all.

### 17. resvg does not stretch; it fits

`resvg -w 32 -h 32` on a 128×64 mark produces a **32×16** PNG. The aspect ratio wins and the
second dimension is derived, so the non-square path was silently emitting non-square
"32 px icons" and an ICO whose 32×32 header disagreed with its own payload.

`preserveAspectRatio="none"` alone does not fix it either — resvg derives the output size
from the SVG's *intrinsic* size (its `width`/`height`, falling back to the viewBox), and
`removeDimensions` has just deleted those. Both halves are needed: a square `width`/`height`
pair put back, and the aspect ratio freed.

It goes on `icon.svg` rather than on a private copy, so the SVG favicon and the PNGs frame the
mark the same way. `logo.svg` does not get it: that one is the mark for pages and READMEs,
where its real proportions are the right ones.

`icoWrap` now reads the payload's IHDR and refuses to write a header that disagrees with it.
That is what turned a silently wrong file into a failed build.

### 18. Two svgo 4.1.0 bugs sit exactly on the animated-input contract

Both are triggered by `@keyframes` inside `@media (prefers-reduced-motion: no-preference)` —
which is the shape §4 of the contract *requires*.

**The crash.** `lib/style.js parseStylesheet` skips a top-level `@keyframes`, because its
percentage selectors are not selectors. For any *other* at-rule it runs an inner
`csstree.walk` that collects every descendant `Rule` with no such guard, so `0%` and `100%`
land in the rule table svgo matches elements against. Everything that resolves a computed
style then feeds them to css-select:

```
Error: Unmatched selector: %   at css-what parse.js:128
  ... css-select is() -> svgo lib/xast.js matches() -> lib/style.js computeOwnStyle()
```

That path is reached from `removeDeprecatedAttrs`, `removeUnknownsAndDefaults`,
`inlineStyles` and more, so disabling one plugin only moves the crash. favcon **hoists** any
`@keyframes` nested in an at-rule out to the top level of the same stylesheet instead, which
removes the input that triggers it. The hoist is safe: `@keyframes` has no cascade and no
conditional behaviour, it only defines a name — what decides whether the mark moves is the
`animation` declaration, and that stays inside the guard.

**The silent one, which is worse.** `inlineStyles` copies a rule's declarations onto the
elements it matches and then deletes the `class` attribute it consumed — without checking
whether a rule it *left alone* still selects that class. It leaves two kinds alone: rules
inside an at-rule (its `useMqs` default of `['', 'screen']` is compared against a string
built as `` `media screen` ``, so in practice nothing inside an at-rule qualifies) and rules
with a pseudo-class. Both are exactly where motion lives. `minifyStyles` then hands csso a
usage list built from the classes still in the document, csso drops the `@media` rule as
unused, and the animation disappears from `logo.svg` with no warning at all.

**The hazard is per name, not per file**, and getting that wrong costs bytes. A name is only
at risk when *both* are true: some rule svgo will not inline selects it, **and** some rule it
will inline selects it too. The common shape — palette classes at the top level, a motion
class named only inside the guard — is perfectly safe, because nothing inlines the motion
class and so nothing strips it. The first version of this check asked the coarser question
("is any class selected inside an at-rule?"), switched inlining off for those marks as well,
and added 44 B to a real seven-block logo whose output had previously been byte-stable.

Three fixes were measured on the animated fixture, through the full plugin list:

| fix | bytes | result |
|---|---|---|
| `inlineStyles` off | **473 B** | guard kept, class kept |
| `inlineStyles removeMatchedSelectors` off | 534 B | guard kept, class kept |
| `minifyStyles usage.classes` off | 445 B | guard kept, **class gone — animation dead** |

The smallest *correct* option wins, and it is only reached when a class is genuinely at risk:
a mark whose motion selects nothing by class still gets the full inlining.

### 19. `--colors` stays at 8, and that is a trade rather than a clean win

The 1.0 % accuracy bar is met at `--colors 16` on every file. It is **not** met at 8 on every
mark that ships here: worst 1.87 % on `heavy.svg` at 192 px, which exists to be adversarial,
with `general`, `flat`, `mask` and `animated` also over at 192, and `flat` (1.11 %) and
`animated` (1.12 %) over on the 180 px apple icon. Every 512 px file is inside at 8 (worst
0.71 %, `heavy`). A small icon is mostly edge pixels. See the table in `docs/BENCHMARKS.md`.

8 is the default anyway, and the reasoning is worth stating plainly rather than hiding behind
the bar:

- It is **~18 % smaller** across the corpus, and bytes are what this tool is for.
- The misses are anti-aliased edges at small sizes and smooth colour ramps. A mark drawn on
  a pixel grid has neither: `tiles.svg` scores **0.00 %** at 8 on every file, `wide` at most
  0.13 %. For such a mark, 16 spends 18 % more bytes to improve nothing.
- The failure mode is graceful and visible — banding on a gradient — not a broken file, and
  `--colors 16` is one flag away with a table saying when to reach for it.

So the bar describes the pipeline's capability, and the default picks a point below it on
purpose. Both halves are pinned by a test: one asserts the default really is 8, the other
asserts 8 really does miss the bar on `heavy` at 192 px. If either stops being true, the trade has
changed and this decision needs rewriting rather than quietly drifting.

### 20. Masked icons at their documented sizes, placed by measurement, snapped to whole pixels

**Which files the platforms read:**

| Consumer | What it reads | Source |
|---|---|---|
| Chrome install criteria | `any` icons at 192 and 512 px (the code on desktop accepts one of 144 px or more) | web.dev, Chrome docs, MDN; `installable_evaluator.cc` |
| Chrome's launcher icon (Android, ChromeOS, macOS) | `maskable` first, falling back to `any`; Android's minimum is 83 px | `installable_icon_fetcher.cc` |
| Android WebAPK | PNG and JPEG are sent to the server; an SVG entry fails the install | `webapk_single_icon_hasher.cc`, crbug.com/40925759 |
| iOS and iPadOS | `apple-touch-icon` over manifest icons; 180, 167 and 152 px documented; `purpose` and SVG ignored | Apple's Configuring Web Applications, firt.dev's iOS PWA notes |
| Windows | `any` icons, drawn without a plate on light and dark | Microsoft Learn, app icon and PWA icon guidance |

**Two masked files, at the documented sizes.** `apple-touch-icon.png` stays 180 px, the largest
size Apple documents. `icon-maskable-512.png` is one 512 px maskable icon, the size web.dev's
and Evil Martians' sets use; Chrome picks it by size and scales it down. An earlier draft of
this decision made a single 512 px `apple-touch-icon.png` serve both. No source recommends a
512 px apple icon, so it was reverted: Apple's guide only says iOS would scale a larger one.

**`any` stays transparent and separate.** Windows shows app icons without a tile, so a padded
opaque icon there reads as a small square; web.dev advises against `"any maskable"` on one file
for the same reason.

**Measured placement.** The farthest opaque pixel's outer corner, found on a render at the
icon's own size, decides the scale. On the C mark, iOS's 22.37 % rounded mask cut 12 of 14 310
mark pixels from the unplaced 180 px icon, and none after.

**Snapped to whole pixels.** An exact fit put every edge of the C mark between pixels:

| Icon | Placement | Mark box | Colours | Edge pixels | Bytes at `--colors 8` |
|---|---|---|---|---|---|
| maskable 512 | exact fit | 330 px | 12 | 1 905 | 571 B |
| maskable 512 | snapped | 320 px | 3 | 0 | 290 B |
| apple 180 | snapped | 112 px (fit 116) | 3 | 0 | 151 B |

The snap walks the box down in whole even pixels (so the offset is whole too) and stops at
10 % below the fit. It takes the size with the fewest partly covered pixels, and only when that
at least halves them, so a curved mark, anti-aliased at every size, keeps its exact fit and is
never shrunk for nothing. The renders are a handful of transparent resvg calls per icon,
milliseconds each, against a build of seconds.
